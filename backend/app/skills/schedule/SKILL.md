# 日程规划

用途：用户明确要求安排、规划、调整日程或排进日历时生成可审核方案；“只看看安排”、引用和假设不触发修改。

必要上下文：当前上海时间、近期用户提供的任务名称/工作时长/截止时间、同一草案的当前版本。先按需用tasks、calendar、preferences读取正式任务、课程、保护时间、可用时间和偏好；数据不足时continue_after_read后再决定，不推断已读完整库。

可使用attention快速取得真实任务优先级和候选空档，time_rules读取固定课程和保护时段。用户同时提出新课程/午休规则时，应先说明并建议确认规则，再基于正式规则生成计划；本轮没有profile_draft权限时不能把规则暗中写入或用文字假装生效。已有复杂任务需要拆解时承接用户要求，在允许breakdown_draft的轮次生成子任务草案，确认后继续聊天安排，不能把未确认任务树当正式任务。

执行：使用planning_draft及原排程引擎/Validator，本周剩余和下周之外不扩大范围。优先使用服务端draft_defaults及schedule_preview_schema；字段缺失可用空arguments请求可信后端生成可编辑初稿，不要求用户先填task_id。预计工作时长默认60分钟；一个半小时=90、两小时=120、半小时=30。日期默认今天，“明天/明晚”为下一自然日；建议起点早上/上午09:00、中午12:00、下午14:00、晚上/今晚19:00，用户明确钟点或适用已确认偏好优先。默认值由代码维护，文字不授予权限。

“明早”为下一自然日早上。先查询真实课程与占用，再按用户要求生成可用的待确认草案。“想九点”“希望九点”优先尝试用户时间，有占用时在用户截止前自动选择其他合法时段，并在首条回复说明占用事项、时间和实际调整结果。只有“必须九点”“固定九点”“不能改时间”等明确要求才使用fixed_start/start_exact；这些要求遇到占用时说明原因并请用户选择。任务名称、工作时长、截止时间及明确固定时间优先于系统默认，课程、保护时间和锁定校验始终生效。草案字段必须反映实际候选时间，最终采用由用户确认。

用户明确需求是本次规划的依据。先区分新活动和对原任务的修改。“我这周六上午想健身，上午九点开始，预计2小时，你帮我规划一下草案”表示本次周六活动。即使库中有同名旧任务，也不能自动引用它的身份、截止时间、锁定或安排限制。只有用户明确修改、重新安排原任务，或已经选中具体任务时，才继承该任务的约束。当前完整活动请求优先于历史对话里其他活动的日期和截止。

明确日期、时段和钟点分别处理。“这周六”按context.now所在周换算，演示时间2026-10-14对应10月17日（周六）。新建、已有任务修改和草案编辑都须用allowed_windows限定该日及用户指定时段。上午为08:00–12:00，中午为12:00–14:00，下午为14:00–18:00，晚上为18:00–22:00；单任务初稿使用time_period保存时段。对应默认起点为09:00、12:00、14:00、19:00，默认起点可以在指定时段内避让课程和正式占用，明确要求固定钟点时才设置fixed_start或start_exact。时段内无法容纳完整工作与休息时保留可编辑草案，说明容量不足，等待用户调整时段或分段要求。preferred_windows只表达允许窗口内的钟点偏好。用户没有提供截止时间时保持为空，不能将开始时间加时长、同名旧任务截止或模型猜测写成用户截止。发生避让时先说明具体占用事项和时间，再说明实际推荐时间，并同步写入草案。确属本次原任务的真实截止与用户日期冲突时，说明依据和需要用户决定的调整，不能强行套用其他任务的限制。

可调整的建议起点已过时，在当前时间之后的合法网格寻找安排。用户明确固定的起点已过时，请用户选择新的时间。排程遵循08:00–22:00、课程、保护时间和锁定约束，所选日期或时段放不下时展示原因。工作时长不含独立休息。没有任务名称时用待命名初稿并禁止直接确认，没有真实截止时保持空值，“今晚想完成”作为完成窗口。正式Task需要DDL，初稿可查看编辑，补真实截止后才可采用。未知类别采用现有合法默认。

新任务可使用原规划草案同时预览任务和候选安排，只有采用方案的原事务才保存。若先拆解，必须先审核创建子任务，再另生成并采用日程，不能融合两个确认。用户明确针对已有任务时引用task:id，同名本身不足以确定任务身份。补全needs_input草案沿用原draft引用；ready草案修改使用已协调的edit_draft及kind/id/version，不覆盖未保存编辑。

结果：有真实planning资源才说“日程草案已生成，请查看并确认采用”；失败说明原因。禁止直接确认、放宽source_revision或安排过去时间。

用户允许分段时按真实空档安排，默认两段，用户指定数量时采用该数量。每段可不等长，工作分钟合计必须等于预计时长。不要先找完整连续时段再机械等分，不凭空安排课程或休息。自动分段的单任务初稿修改segments并清空work_segments，由原算法填入实际各段起止，通用动作使用profile.segment_count明确段数，splittable=true并由原排程算法计算。用户明确提供各段起止时才填写work_segments，手动时间逐段校验课程、锁定、截止和重叠。没有足够空档时给出具体原因，不能减少任务时长或悄悄改段数。

对已有日程草案重新分段使用split_draft，按split_schema传入已协调的id、version、content和target。先将content中的segments或目标profile.segment_count设为用户要求数量。聊天与表单按钮使用同一分段工具，正式写入仍需确认。

面向用户的回复只保留本次任务的日期、实际安排、时长和需要处理的问题。正常结果用两三句话，发生调整先说明占用事项与时间，再说明实际安排。失败写清“什么挡住了安排、可以改哪里”。不输出无关任务的过期或剩余时长通知、复盘演示记录、整个任务库诊断、内部字段或重复确认说明。后台通知用于保护历史，不能直接粘贴成用户的分析报告。

正例：前文“今晚写操作系统作业”，后文“90分钟，帮我安排”→继承名称与今晚、读取正式约束，缺DDL也先生成有真实ID的可编辑初稿。再说“改成晚上八点，两小时”→更新同一草案。反例：“先不要帮我安排”→不生成。测试：默认来源、无DDL、课程冲突、21点剩余容量、分段休息、旧版本、重试和确认前无正式日程。
